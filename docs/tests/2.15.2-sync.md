## Implementation notes

`CampaignNetwork` registers only a clientbound play payload, protocol version 1. It uses the immutable `PlayerCampaignView` projection; no future campaign definition or raw save object is serialized. There is no serverbound Advance/Claim request yet (2.15.3).

`CampaignRuntime` queues delivery after successful start/progress/advancement/claim mutations and after compatible reloads. Login/rejoin, respawn and dimension changes also queue snapshots. `CampaignSyncService` drains each affected player's queue once per server tick and uses `PacketDistributor.sendToPlayer`, never a broadcast. A receiver's delivery sequence is separate from player save revision and resets for a new connection.

Client handlers run on the NeoForge main thread. `ClientCampaignState` binds snapshots to the current connection, rejects late/duplicate sequences or an unexpected session, and clears state on disconnect. The physical-client-only event subscriber owns connection events and `/tamclient state`; the common networking classes reference no Minecraft client classes, keeping server classloading separate. Further action/cache consistency work remains 2.15.4.

The codec rejects snapshots over 512 KiB, lists over 4096 entries and strings over 8192 characters. It never silently truncates authorized data. Large-history paging/chunking is required before campaigns exceed these limits; this basic full-snapshot transport does not claim unlimited history support. Cosmetic reloads send a new delivery sequence even when the player revision is unchanged.
