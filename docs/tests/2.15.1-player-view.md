## Contract for the networking step

Use **`CampaignRuntime.getPlayerView(ServerPlayer)`** to obtain the payload's presentation data. It requires the server thread and the actual connected player, and reads quest/reward state from one detached `CampaignSavedData.PlayerSnapshot`. It accepts no client-selected UUID.

`PlayerCampaignView` contains only immutable presentation records, lists, strings, amounts, flags, optionals and the server session UUID:

- The active quest, mandatory/optional objective amounts, completion/readiness and ingredient quantities.
- Completed history, including final optional amounts. Known entries follow manifest order; missing historical definitions follow in ID order with a neutral label. This is not chronological history or a save-migration system.
- Earned XP/item reward entries for completed quests, with their saved amounts and individual claim states. These come from the earned ledger, never current reward definitions. Inconsistent active/future reward groups are excluded.
- Initialization/completion state, the server session ID and the player snapshot revision.

There is no future quest list, next quest ID, campaign total, unearned reward catalogue, raw trigger, player UUID, mutable domain object, Minecraft registry or server object in the shared view. History may reveal only completed quests; ingredients belong to the active/history objectives already allowed to that player.

The **player revision** tracks saved player changes. A compatible cosmetic definition reload can change the presentation without changing that revision. The networking step must send refreshed presentation after an accepted reload and use a separate delivery sequence where needed; it must not discard such a refresh merely because player revision is unchanged. Server session identity is not a per-connection token.

Invalid objective amounts are rejected rather than silently rewriting saved progress. Missing active definitions fail clearly. Broader definition migration remains an existing separate issue.
